1. Executive Summary & Problem Statement

University hostel allotment is traditionally conducted manually using fragmented spreadsheets and ad-hoc email communications. In large residential institutions housing thousands of students, this legacy methodology suffers from significant operational flaws:

  • Complex Constraint Conflict: Manual managers struggle to satisfy multi-tiered criteria simultaneously, including capacity limits, gender-segregated blocks, affirmative action quotas (Sports, PWD, International, Scholarship), fee status, and medical accessibility requirements.
  • Lack of Explainability & Auditability: When allotment decisions are contested by students or parents, spreadsheet administrators cannot furnish verifiable audit trails explaining why an applicant was placed in a specific bed or waitlisted.
  • Privacy Vulnerability: Sensitive lifestyle questionnaire data (sleep habits, noise tolerance, smoking status) is routinely handled in plain-text spreadsheets, violating student privacy standards.

The Solution: This project introduces a full-stack, enterprise-grade, policy-driven allocation system. It replaces spreadsheets with a deterministic allocation engine capable of processing 8,000+ applicants across 2,960 rooms in under 1.5 seconds. It enforces immutable state governance, cryptographic field-level encryption for lifestyle surveys, append-only hash-chained audit logging, and dynamic role-based dashboards for all university stakeholders.

3. Core Engineering Invariants & Security Principles

The architecture guarantees 8 non-negotiable operational invariants enforced simultaneously at the engine, database hook, and API gateway levels:

  • Invariant I1 (Draft/Published Separation): Draft status transitions through a strict finite state machine: GENERATING → DRAFT → UNDER_REVIEW → APPROVED → PUBLISHED. Exactly one guarded code path (DraftPublishService.publish()) can mark a draft published, requiring an authentic Chief Warden approval hash.
  • Invariant I2 (Immutability Post-Publication): Once published, assignments and explanations are mathematically sealed and cannot be edited or deleted. Post-publish changes require audited change records.
  • Invariant I3 (Deterministic Reproducibility): Given the same input snapshot, seed, and policy version, the engine produces byte-identical assignments (verified with seeded sfc32 PRNG).
  • Invariant I4 (Explainability): Every assignment generates a human-readable and structured audit reason detailing preference rank matched, quota category, compatibility score, and tiebreaker values.
  • Invariant I5 (Mandatory Override Audit): Any manual room reassignment by a warden requires a categorized, non-empty justification (≥10 characters) and automatically escalates to the Chief Warden if a hard constraint is touched.
  • Invariant I6 (Lifestyle Privacy): Questionnaire responses are encrypted at rest with AES-256-GCM (per-record IV + key versioning). Wardens and administrators only receive aggregate pairwise compatibility scores (0–100); raw answers are never exposed.
  • Invariant I7 (Cryptographic Audit Ledger): Append-only SHA-256 hash-chained log where every transaction embeds the hash of the previous block, providing tamper-evident traceability.
  • Invariant I8 (Hard Constraint Enforcement): Engine guarantees zero double-booked beds, strict adherence to gender-segregated blocks, accessibility matching, and quota ceilings.
